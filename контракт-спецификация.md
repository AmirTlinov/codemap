# Контракт-спецификация flagship-карты codemap

## Статус и владение

Этот документ — контракт дореализации `codemap` до flagship-карты
для агента. Он владеет целевым поведением, порядком вертикальных
срезов и условиями, при которых продукт можно считать завершённым.

Существующие владельцы сохраняются:

- [`docs/PRODUCT.md`](docs/PRODUCT.md) владеет стабильными продуктовыми
  инвариантами и публичной CLI-поверхностью;
- [`docs/IMPLEMENTATION.md`](docs/IMPLEMENTATION.md) владеет текущим
  устройством модулей;
- [`docs/CURRENT_LIMITATIONS.md`](docs/CURRENT_LIMITATIONS.md) владеет
  наблюдаемыми пробелами и границами утверждений;
- [`docs/BENCHMARK_AB.md`](docs/BENCHMARK_AB.md) владеет механикой
  парного поведенческого измерения;
- [`docs/SCHEMA_POLICY.md`](docs/SCHEMA_POLICY.md) владеет compatibility-
  правилами публичных JSON-схем;
- [`docs/plans/feature/PLAN.md`](docs/plans/feature/PLAN.md) и
  [`docs/plans/feature/TODO.md`](docs/plans/feature/TODO.md) остаются
  историей уже закрытых границ, но не заменяют новый flagship-контур.

Если старая отметка `closed` противоречит наблюдаемому пробелу, приоритет
имеет живое поведение и этот контракт. Зелёный тест доказывает
стабильность защищённой границы, а не завершённость всего продукта.

### Нормативный язык

`обязан`, `не может`, `только` и условия `закрыто, когда` являются обязательными
требованиями. `следует` обозначает предпочтительную реализацию, от которой можно
отступить только с receipt, сохраняющим тот же наблюдаемый контракт. Примеры
иллюстрируют форму, но не расширяют поддерживаемую семантику без явного правила.

## 1. Сильная форма продукта

`codemap` — это детерминированная прогрессивная карта внимания для
кодирующего агента. Она показывает:

1. что фактически есть в запрошенной области;
2. какие стороны связаны наблюдаемыми отношениями;
3. где проходят runtime-, contract-, data-, deployment- и verification-границы;
4. какая часть карты была показана, скрыта, не поддержана или осталась
   динамически неразрешимой;
5. какой точный запрос раскроет следующий слой без повтора всей уже
   показанной энциклопедии.

`codemap` не выбирает, что агенту исправлять. Он не оценивает архитектуру,
не присваивает файлу звание «лучшего», не делает вывод о корректности и не
превращает verification surface в вердикт. Он даёт агенту лучшую
наблюдаемую карту, чтобы агент сам понимал, проверял и действовал.

### Flagship-критерий

Инструмент становится необходимым любому агенту не потому, что он
заставляет всегда строить большую карту, а потому, что любой агент в любом
проекте может дешёво спросить:

> «Какая структурная правда вокруг моего текущего якоря?»

и получить ответ, соразмерный неопределённости:

- точный локальный anchor — короткая локальная карта;
- незнакомый домен — карта текущего уровня;
- многофайловое изменение — карта изменившихся связей и проверок;
- динамическая или неподдержанная связь — явный край видимости, а не догадка;
- отсутствие значимых связей — короткий нулевой ответ, а не ритуальный обход.

## 2. Неизменные инварианты

Каждый вертикальный срез обязан сохранять эти свойства.

### 2.1. Карта, а не суд

`codemap` может сообщить:

- обнаружено;
- связано;
- связь опосредована;
- совпадает только по мягкому признаку;
- скрыто лимитом;
- не поддержано экстрактором;
- невозможно статически разрешить;
- найдена verification surface;
- найдена исполняемая команда;
- не найдена прямая связь.

`codemap` не может сообщить:

- лучший файл;
- правильная архитектура;
- рекомендованное исправление;
- безопасно удалять;
- тестов достаточно;
- изменение корректно;
- связей больше нет;
- динамическая граница не важна.

### 2.2. Правда имеет происхождение

Каждый agent-facing факт имеет:

```txt
entity or relation
evidence kind
evidence strength
one or more source locations
extractor identity/version
freshness snapshot
```

Выводимая связь не может быть сильнее её самого слабого звена. Документация,
комментарий, имя и соседство не превращаются в runtime-, consumer-, contract- или
verification-факт без дополнительного структурного свидетельства.

### 2.3. Неполнота явна

Любая ограниченная карта показывает горизонт видимости:

```txt
observed:    сколько фактов извлечено в запрошенном scope
shown:       сколько показано в этом ответе
hidden:      сколько скрыто лимитом и по каким группам
unsupported: какие файлы/конструкции не разобраны
dynamic:     какие связи обозначены, но не разрешены статически
```

Горизонт видимости — не confidence score. Он не оценивает истинность вывода;
он показывает границы построенной карты.

Любой количественный факт, который может выключить внимание агента, хранится не
голым числом, а парой наблюдаемого количества и замкнутости обхода:

```txt
ObservedCount {
  observed: u64
  closure: closed | open(reason[]) | unavailable(reason[])
  certificate_id: CoverageCertificateId
}
```

Readable-формы выводятся однозначно:

```txt
counted(n)                    observed=n, closure=closed, n>0
proven-zero                  observed=0, closure=closed
counted-at-least(n, reason)  observed=n, closure=open, n>=0
unknown(reason)              closure=unavailable; надёжный обход не начат
```

`counted-at-least(0, reason)` предпочтительно рендерится как `unknown lower bound: 0`,
чтобы агент не прочитал его как доказанный ноль. Plain `0` разрешён только как
короткая форма `proven-zero`. В JSON всегда присутствуют `observed`, `closure`,
`reasons` и `certificate_id`.

`CoverageCertificate` является машинным основанием `closure`:

```txt
CoverageCertificate {
  id
  query_kind
  scope
  snapshot
  eligible_files
  visited_files
  excluded_files_by_reason
  extractor_capabilities[] { extractor_id, version, language, constructs[] }
  unsupported[] { file, construct, location? }
  dynamic_stops[] { kind, location, missing_surface }
  external_stops[] { kind, location? }
  closure: closed | open(reason[]) | unavailable(reason[])
}
```

`closure=closed` допустим только когда все eligible files посещены, каждый
релевантный construct входит в объявленную capability и нет unresolved stop,
способного добавить элемент считаемой категории. Само отсутствие parser error не
доказывает closure. Тотальный `unknown` там, где closure доказуема, является таким
же дефектом карты, как ложный ноль.

### 2.4. Ноль так же важен, как находка

Если в точном scope нет наблюдаемых потребителей, контрактов или verification
surfaces и certificate доказывает `closure=closed`, карта возвращает `proven-zero`,
говорит «не найдено в полностью обойдённом поддержанном scope» и завершается. Если
найдены элементы, но обход не замкнут, она возвращает `counted-at-least(n, reason)`;
если надёжный обход невозможен — `unknown(reason)`. Она не добавляет мягкие
совпадения только ради заполнения ответа.

### 2.5. Прогрессивное раскрытие монотонно

Каждая команда `Expand`:

- сохраняет исходный anchor;
- называет раскрываемую группу;
- добавляет один слой деталей;
- не повторяет без необходимости всю предыдущую карту;
- не называется «рекомендованной» и не скрывает альтернативные группы;
- является точной и исполняемой командой.

Одна скрытая группа имеет один счётчик и одну ручку `Expand`. Один факт в одной роли
перечисляется в кадре один раз. Другие секции могут показать его агрегатный счётчик
или ссылку на единственную секцию-владельца, но не повторить список.

### 2.6. Операционные инварианты

- один внешний binary;
- однозначная version/build provenance;
- нуль записей в целевой репозиторий по умолчанию;
- внешний cache с явной свежестью;
- никакого network access в map path;
- никакого запуска project commands без `--run`;
- никакого LLM, embeddings, semantic ranking и task routing в hard path;
- любой кеш-сбой ведёт к перестроению или явной деградации, а не к тихой ложной
  карте.

### 2.7. Краткая проверочная форма K1–K10

Эти аксиомы — короткая review-поверхность всего контракта. Нарушение любой из них
в agent-facing output — дефект карты.

- **K1. Provenance:** каждый факт имеет evidence и, где формат позволяет, `file:line`.
- **K2. Честный ноль:** `0` означает certificate-backed `proven-zero`; частичный обход
  даёт `counted-at-least`, а невозможный — `unknown`.
- **K3. Не суд:** вывод содержит факты, границы и координаты, не вердикты и советы.
- **K4. Полнота по ширине:** каждая наблюдаемая категория присутствует в кадре фактом или счётчиком.
- **K5. Одна ручка:** одна hidden-группа имеет один счётчик и один exact `Expand`.
- **K6. Один факт — один раз:** одно ребро или поверхность в одной роли не дублируются между секциями.
- **K7. Исполняемый Expand:** каждая напечатанная команда синтаксически валидна и показывает обещанную группу.
- **K8. Детерминизм и нулевой след:** один вход даёт одну карту; целевой repo не изменяется.
- **K9. Fail-honest:** unsupported, dynamic и ambiguous становятся typed unknown, а не guessed edge или молчание.
- **K10. Когнитивный бюджет:** лимит каждой daily-линзы является исполняемым regression gate.

## 3. Универсальный контракт использования

Инструмент не знает задачу агента и не должен её угадывать. Соразмерность
задаётся не task router, а формой запрошенного anchor.

| Ситуация агента | Первый запрос | Достаточная первая карта |
| --- | --- | --- |
| Точно известен файл | `codemap cone <file> --depth 1` | Входы, выходы, потребители, границы, verification и unknown |
| Известен символ | `codemap where <symbol>` | Все точные определения без ranking; для одного — X-Ray |
| Известен пакет/домен | `codemap ls <scope>` | Текущий уровень, owner surfaces, контейнеры и переходы |
| Репозиторий незнаком | `codemap ls .` | Ограниченная карта доменов, packages, runtime, contracts, data, CI и proof containers |
| Есть накопленное изменение | `codemap changed --since <snapshot>` | Только новая структурная разность текущей сессии |
| Нужно понять проверки | `codemap proof <anchor\|changed>` | Топология verification surfaces и команд, не вердикт достаточности |
| Нет распознанной структуры | тот же exact/root запрос | Короткий inventory, unsupported/unknown и ноль выдуманных связей |

Поэтому «используется в любом случае» не означает «всегда выполняет полный
root-обход». Универсальность достигается дешёвым точным входом, а не
обязательной энциклопедией.

## 4. Прогрессивная лупа внимания

Один и тот же фактовый слой проецируется на пять масштабов.

```text
L0  Repository orientation
    domains / packages / runtime / contracts / data / CI / proof containers
                         |
L1  Scope map             v
    current-level children / crossings / public and runtime surfaces
                         |
L2  Anchor X-Ray          v
    inputs / outputs / consumers / state / effects / verification / unknowns
                         |
L3  Cross-owner path      v
    execution / contract / data / deployment transformations and stops
                         |
L4  Change and proof      v
    structural delta / affected paths / verification topology / missing links
```

Переход между уровнями делает агент. `codemap` не объявляет более глубокий
уровень нужным; он показывает, что там есть и как это открыть.

### 4.1. Контракт bounded output

| Проекция | Строк по умолчанию | Приблизительный token ceiling (`ceil(chars/4)`) |
| --- | ---: | ---: |
| root `ls .` | 120 | 1500 |
| exact `cone <anchor> --depth 1` | 90 | 1100 |
| `changed` до 150 files | 130 | 2000 |
| `proof changed` | 90 | 1200 |
| `where` с одним definition | 60 | 700 |

Формула приближённого token count зафиксирована для regression comparison; она не заменяет
точную tokenizer-specific стоимость.

- видимые элементы группируются по классу и owner container, а не по общему
  алфавитному top-N;
- каждая усечённая группа имеет ровно один `hidden_count` и один exact expand;
- каждое ребро/поверхность в одной роли печатается один раз;
- `--brief` убирает повторный prelude и разъяснения, но не факты, unknowns и
  visibility horizon;
- JSON полностью сериализует все наблюдённые facts, relations и coverage gaps внутри
  запрошенного scope и schema-versioned; это не является заявлением о семантической
  полноте неподдержанных или dynamic частей. Markdown остаётся ограниченной проекцией.

Эти budgets являются hard regression bounds для текущего readable contract, но не
доказательством когнитивной оптимальности. Их можно ужесточить по измерению; ослабить —
только вместе с paired A/B receipt, показывающим, какая дополнительная полнота куплена.
Snapshot-update или рост fixture сами по себе не являются основанием поднять лимит.

### 4.2. Диверсифицированное, а не ранжированное ограничение

Когда все элементы не помещаются, карта не угадывает «самые важные». Она
детерминированно показывает представителей разных фактовых групп:

```txt
package/domain
public contract
runtime entry/route/job
data/schema/migration/storage
config/env/secret declaration and reader
CI/release/deployment
verification command/sensor
generated/asset/event
unknown/unsupported/dynamic boundary
```

Это не ranking: классы заданы онтологией карты, порядок внутри класса
стабилен, а скрытый остаток измерим.

## 5. Единая онтология карты

Все линзы — проекции одного фактового графа. Ни одна линза не получает
собственный парсер или параллельную классификацию уже представленного факта.

### 5.1. Сущности

```txt
Repository
Scope
Domain
Package
File
Symbol
Surface
Command
RuntimeEntry
RuntimeRoute
MiddlewareOrGuard
Contract
Schema
Migration
DataStore
EnvironmentKey
ConfigValue
EventChannel
GeneratedArtifact
Asset
Workflow
DeploymentSurface
VerificationSurface
ReceiptOrWitness
```

Новая сущность добавляется только если она несёт отличающуюся картографическую
функцию. Имя домена или архитектурное толкование не являются достаточным
основанием.

### 5.2. Отношения

```txt
contains
declares
```

### 5.3. Доказательство

| Strength | Допустимое основание | Что оно доказывает | Чего оно не доказывает |
| --- | --- | --- | --- |
| Hard | manifest, exact syntax, explicit config, normative semantic anchor | Только прямо объявленную сущность или связь | Фактическое runtime-исполнение и корректность |
| High | statically resolved import/use/reference/registration | Наблюдаемый статический путь с exact location | Dynamic dispatch, фактический вызов и полноту всех путей |
| Medium | convention плюс независимое структурное подтверждение | Вероятную structural surface, явно маркированную как conventional | Consumer, runtime, contract или verification relation без дополнительного evidence |
| Soft | name, token, path proximity, docs, comments | Координату для ручного внимания или отдельный related bucket | Первичную relation любого типа |

`exact convention` не является Hard: точность распознавания convention не превращает
её в явное объявление. `.codemap.yml` semantic anchor является `Hard(declared)` только
для записанной в нём архитектурной сущности или границы; он не повышает runtime-,
consumer- или verification-связь без независимого syntax/config evidence. Запрошенный
anchor является координатой scope, а не evidence отношения.

Strength описывает силу наблюдаемого свидетельства, а не вероятность того, что
агенту следует менять данную сторону. `unsupported`, `dynamic`, `ambiguous` и
`external` являются состояниями coverage, а не низкими strength.

Для составного пути итоговая strength равна самому слабому ребру. Renderer не может
повысить strength; повышение разрешено только extractor/model owner с новым source
location и regression, доказывающим дополнительное основание.

### 5.4. Unknown как край карты

Каждый `Unknown` содержит:

```txt
kind
anchor
where
observed precursor
why unresolved
what part of the map may be absent
exact expansion or manual evidence surface, when one exists
```

Unknown не содержит совета по исправлению.

### 5.5. Нормативная машинная оболочка

Каждый public JSON report является полной сериализацией **наблюдённого набора
фактов и его горизонта**, а не утверждением о полной семантике репозитория.
Минимальная общая оболочка:

```json
{
  "schema_version": "...",
  "report_kind": "...",
  "build_identity": {},
  "scope": {},
  "snapshot": {},
  "facts": [],
  "relations": [],
  "counts": {},
  "coverage_certificate": {},
  "unknowns": [],
  "expands": []
}
```

Обязательные правила:

- каждое `fact` и `relation` имеет стабильную identity, evidence, strength и locations;
- каждый count разрешается в тот же `CoverageCertificate`, что и соответствующий
  список фактов;
- `expands` содержит argv-массив как нормативную форму; shell string является только
  readable-проекцией с корректным quoting;
- valid empty map имеет успешный typed result и не смешивается с invalid anchor;
- отсутствие optional field не может означать одновременно «ноль», «не поддержано»
  и «не вычислялось»;
- Markdown является bounded-проекцией этой оболочки и не содержит факта, которого
  нет в JSON/model layer.

Golden contract suite обязан иметь по паре Markdown/JSON минимум для root atlas,
exact symbol, partial count, `proven-zero`, typed unknown, hidden group с Expand и
`changed`/`proof changed`.

Машинная оболочка вводится поэтапно, а не одним скрытым переломом:

- S01 добавляет `build_identity`, S03 — counts/horizon/certificates, а каждый
  затронутый report в том же срезе получает явный schema-version bump;
- до S14 эта оболочка имеет статус `flagship-v1-draft`: она проходит schema
  validation, но не обещает замороженную внешнюю compatibility;
- каждый срез, меняющий JSON, обновляет `schemas/manifest.json`, regression
  fixtures и migration note по [`docs/SCHEMA_POLICY.md`](docs/SCHEMA_POLICY.md);
- S14 фиксирует первую stable agent envelope и exit taxonomy. После этого
  несовместимое изменение требует новой major schema version и отдельный
  compatibility receipt.

## 7. Технический поток

```text
repository discovery
        |
        v
inventory + git truth
        |
        v
language/config/runtime extractors
        |
        v
single normalized entity/relation/evidence graph
        |
        +--------------------------+
        |                          |
        v                          v
external incremental cache     coverage horizon + unknown ledger
        |                          |
        +------------+-------------+
                     v
             scoped projections
                     |
                     v
       bounded Markdown / complete scoped JSON
```

Архитектурные правила:

1. `src/repo` извлекает факты, но не решает, какая линза их покажет.
2. `src/model` владеет единой онтологией, evidence и unknown.
3. `src/map` только проецирует и ограничивает общие факты.
4. `src/render` не реклассифицирует evidence и не изобретает связи.
5. `src/cli` оркестрирует scope, format и execution safety, но не становится
   вторым map engine.
6. `src/cache` кеширует ту же модель с версионной свежестью; cache miss не
   меняет семантику отчёта.

Ограничение 500 строк не считается архитектурной декомпозицией. Каждый
модуль должен иметь одну объяснимую причину изменения. Срез, который
требует синхронного редактирования десятков мелких модулей, не завершён.

## 8. Форма каждого вертикального среза

Срез не является набором разрозненных internal-задач. Он обязан провести одно
поведение от реального репозитория до agent-facing output и проверить его в живом
сценарии.

Каждый срез содержит:

```txt
world after slice
one decisive user/agent scenario
existing owner modules
fact/model change
projection and readable output
schema/compatibility change
focused regression
live dogfood or behavioral A/B
performance/cognitive receipt
explicit exclusions
closure statement
```

### 8.1. Причинное ядро и граница распространения

Даже shared-механизм начинается не как горизонтальный refactor, а как наименьший
сквозной путь, меняющий поведение одного настоящего запроса:

```text
live failure
  -> existing extractor/model owner
  -> shared fact or invariant
  -> one public projection
  -> readable + JSON result
  -> focused regression
  -> live or paired receipt
```

До перевода среза в `Active slice` его activation patch и будущий receipt обязаны назвать:

- `pilot`: один exact command/repo/anchor, где новое поведение впервые становится реальным;
- `primary existing owner`: существующий модуль/тип, через который проходит pilot;
- `propagation boundary`: конечный список следующих проекций или ecosystems;
- `stop rule`: условие, при котором распространение останавливается и оформляется
  новым срезом вместо расширения текущего;
- `non-regression`: предыдущий decisive scenario, который новая общая механика не ломает.

Общая абстракция извлекается из прошедшего pilot, а не создаётся заранее для всех
линз. Массовая миграция до agent-facing receipt pilot запрещена. Если propagation
boundary нельзя обозреть одним review и одним full gate, она делится на именованные
подсрезы `Sxx.a`, `Sxx.b`; в один момент активен только один из них.

### 8.2. Closure receipt

Статус `closed` допустим только при наличии manifest:

```txt
slice_id + contract_revision
before_failure + exact reproduction argv
after_behavior + exact reproduction argv
primary owner files
schema/cache compatibility impact
focused regression ids
live repo + commit + dirty fingerprint
binary identity + hash
readable/json artifact hashes
cognitive/performance measurements
zero-repo-footprint result
excluded behavior
known remaining boundary
full gate result
review identity
```

Receipt не обязан храниться в git, но его hash и расположение фиксируются рядом со
статусом среза. Нельзя закрыть срез ссылкой только на commit, snapshot или зелёный CI.

Срез не закрывается только потому, что:

- добавлен тип в model;
- добавлен renderer snapshot;
- fixture проходит;
- вывод выглядит убедительно.

Он закрывается, когда агент в реальном сценарии получил более полную или более
точно ограниченную карту, а не просто больше текста.

### S00. Контрактная рамка и воспроизводимый baseline

**Мир после среза:** для flagship-волны существует один исполнимый контракт и
неизменяемый baseline. Старые `closed` не маскируют новые наблюдаемые дыры.

**Сквозной сценарий:** разработчик открывает таблицу срезов и может однозначно
ответить, что уже доказано, что не доказано и какой один срез активен.

**Владельцы:** операционная таблица этого документа; existing benchmark/doctor
surfaces для получения receipts. `TODO.md` не владеет статусом flagship-волны.

**Pilot:** воспроизвести B01–B12 из одной атрибутированной worktree binary и заморозить
manifest каждого наблюдения. Primary existing owner — этот контракт плюс current
doctor/benchmark harnesses.

**Propagation boundary:** только baseline/status/receipt surfaces. Stop rule — никакое
исправление B01–B12 не входит в S00, а передаётся владеющему следующему срезу.
Non-regression — zero repo footprint и неизменное поведение daily commands во время
сбора baseline.

**Реализация:**

- вести flagship ledger S00–S17 только в операционной таблице этого документа;
- заменить возможный дублирующий ledger в `TODO.md` одной ссылкой на active slice;
- зафиксировать current release, worktree candidate и installed binary как три разных состояния;
- сохранить baseline-артефакты под `target/flagship-baseline/`, не в целевых репозиториях;
- записать конкретные живые failures из `CURRENT_LIMITATIONS.md` как acceptance fixtures,
  а не как общий backlog;
- заморозить добавление новых линз до S11.

**Доказательство:** docs links, `git diff --check`, `scripts/capture-flagship-baseline.py`
и baseline manifests с binary/hash/repo/SHA/command.

**Исключено:** перенос реализации срезов в новый planning service, дублирование статусов
в нескольких документах, признание старого `closed` новым flagship receipt.

**Закрыто, когда:** новая волна имеет один ledger; ни один из известных дефектов не
исчез из-за старого «final audit passed».

### S01. Одна исполнимая правда

**Мир после среза:** агент, benchmark и developer всегда знают, какой именно `codemap`
построил карту.

**Сквозной сценарий:** в worktree есть build `0.2.x`, а в PATH другая версия. `doctor` показывает
оба executable, версии, build identity и mismatch. Benchmark не может тихо измерить PATH-копию.

**Владельцы:** `src/cli`, `src/map/status.rs`, render status/doctor, benchmark scripts.

**Pilot:** на текущем repo candidate build `0.2.39` запускается рядом с PATH
`0.2.33`; `doctor` впервые обязан назвать оба executable и mismatch. Primary existing
owner — current doctor/status projection, а не новый identity service.

**Propagation boundary:** doctor/status и два существующих benchmark harness. Stop rule —
release/install automation и network lookup остаются вне S01. Non-regression — daily map
commands не хешируют binary и сохраняют текущий zero-repo-footprint.

**Реализация:**

- ввести `BuildIdentity { semver, cache_format, schema_manifest_version, executable_path,
  binary_sha256?, source_commit?, dirty_build? }`;
- не хешировать binary на каждом daily request; рассчитывать hash в diagnostics/benchmark;
- добавить PATH-resolution в `doctor` без запуска чужого project code;
- в `benchmark-codemap-value.py` предпочитать explicit `--codemap-bin`, затем local target,
  затем PATH; всегда сохранять version/hash;
- тот же identity добавить в A/B fingerprint и report prelude JSON.

**Доказательство:** fixture с двумя fake binaries; live current-repo mismatch; benchmark receipt
с exact hash.

**Исключено:** auto-install, auto-update, network version check.

**Закрыто, когда:** ни один отчёт о качестве или производительности невозможно
атрибутировать не той сборке.

### S02. Универсальный соразмерный вход

**Мир после среза:** любой agent task имеет дешёвый соразмерный вход в карту.

**Сквозной сценарий A:** задача называет `src/pricing.py#calculate`. Агент вызывает exact X-Ray,
получает короткую карту и не платит за root-обход.

**Сквозной сценарий B:** агент не знает repo. `ls .` показывает карту текущего уровня
и не вываливает рекурсивный inventory.

**Владельцы:** existing `ls`, `cone`, `where`, CLI help, bootstrap, README, cognitive gates.

**Activation patch:** pilot —
`target/debug/codemap --root /tmp/codemap-s01-integration where status_report` на
текущем repo: одно точное определение без lookup-level unknowns; X-Ray честно
сохраняет один `unsupported_symbol_flow`. Primary existing owners —
`src/cli/args.rs`, `src/map/symbols/where_locator.rs` и текущие
`ls`/`cone` renderers; новый router или service не создаётся. Propagation boundary —
top-level help, README/bootstrap, exact file/symbol/directory/root contracts, compact empty
response и cognitive gates/simple negative A/B. Stop rule — prompt parsing, task
classification, ranking, recommendation и routing остаются вне S02; evidence

### S10. Топология verification без вердиктов

### S11. Диверсифицированное bounded-раскрытие

**Мир после среза:** bounded map остаётся компактной, но не скрывает целые классы
поверхностей из-за общего top-N.

**Сквозной сценарий:** runtime root с сотнями routes/env/jobs показывает ограниченные
представительства каждой fact group, exact counts и отдельные expands.

**Владельцы:** shared projection/budget engine, render helpers, every bounded lens.

**Pilot:** `codemap cone src/model/lens_reports.rs --depth 1` устраняет повтор
verification-фактов между X-Ray и Links и сводит hidden-группу к одному count/Expand.
Primary existing owner — current cone projection/renderer, не новый global framework.

**Propagation boundary:** после pilot `BoundedProjection` принимают `where`, root `ls`,
`changed`, `proof` и глубокие линзы по отдельным `S11.x` receipts. Stop rule — миграция
останавливается, если линза требует новой fact-group semantics или меняет JSON contract.

**Реализация:**

- создать один `BoundedProjection` с group quotas, stable order, counts и expands;
- группы задаются онтологией, а не query/task score;
- убрать private limiter logic из individual renderers;
- expand по group сохраняет anchor, selector и output mode;
- при пустой группе не заполнять бюджет soft noise;
- добавить property tests: deterministic, monotonic, no duplicate identities, exact hidden total;
- добавить invariant: одно ребро `(from, kind, to)` или одна поверхность в одной роли
  не повторяется между Card/Links/Proof/Hidden;
- расширить dogfood harness: собрать все напечатанные `Expand`, исполнить их на
  fixtures и self-repo и проверить `exit 0`, непустой stdout и раскрытие обещанной группы.

**Доказательство:** adversarial mass fixture, reordered inventory fixture, no-duplicate fact set comparison,
executable-Expand harness, large live repo comparison, line/token gates.

**Исключено:** relevance ranking, risk scoring, task-specific selection.

**Закрыто, когда:** перестановка путей не меняет состав фактовых групп в карте, а лимит
не скрывает масштаб остатка.

### S12. Инкрементальная скорость и правда cache

**Мир после среза:** карта достаточно быстра для рефлекса агента, а cache не может
тихо подменить правду.

**Сквозной сценарий:** large dirty repo со 100 изменёнными файлами выдаёт `changed` и
`proof changed` в пределах warm budget, пересчитывая только затронутые facts/indexes.

**Владельцы:** `src/cache`, git probe, fingerprints, fact indexes, doctor timings, dogfood harness.

**Pilot:** `changed --since <snapshot>` на текущем dirty worktree повторно использует
per-file facts и один affected reverse index, не меняя selected set или output. Primary
existing owner — current changed snapshot/cache path.

**Propagation boundary:** `proof changed`, exact `where`/`cone`, root `ls`, затем прочие
artifact caches. Stop rule — ни один новый cache layer не добавляется без phase profile,
semantic parity test и corruption fallback.

**Реализация:**

- профилировать dirty `changed` по phases, а не оптимизировать по предположению;
- кешировать per-file extracted facts и перестраивать только affected reverse indexes;
- делать writes atomic; ошибки read/parse/write учитывать в diagnostics, а не глотать без следа;
- stale/corrupt artifacts удалять или quarantine с явным receipt;
- добавить hidden diagnostic cache status/gc/clear surface с явной мутацией только вне repo;
- описать cache contents, permissions, retention и privacy;
- включить strict performance gate в release/nightly, а не оставлять его advisory.

**Целевые budgets:**

| Path | Small | Medium | Large |
| --- | ---: | ---: | ---: |
| warm exact `where`/`cone` | 100 ms | 300 ms | 700 ms |
| warm `ls .` | 150 ms | 500 ms | 1 s |
| warm `changed` | 300 ms | 1 s | 2 s |
| warm `proof changed` | 300 ms | 1 s | 2 s |
| cold scan | 1 s | 5 s | measured and explained, target 15 s |

Budgets измеряются на зафиксированных fixture/live classes; отчёт сохраняет hardware/OS,
binary hash, cold/warm state и repo scale.

**Доказательство:** deterministic perf fixture, current dirty worktree, large monorepo, corruption/write-failure tests.

**Исключено:** distributed cache, daemon as a requirement, repo-local index.

**Закрыто, когда:** daily warm path проходит hard budgets, а cache failure не может дать агенту
необозначенную stale map.

### S13. Покрытие экосистем и правда о неподдержанном

**Мир после среза:** в любом проекте `codemap` либо показывает поддержанную карту,
либо точно обозначает, какой слой не разобран. Он не создаёт ложную кросс-языковую
полноту.

**Сквозной сценарий:** mixed monorepo с JS/TS, Rust, Python, Go, Swift, SQL, YAML, shell и generated
clients показывает coverage matrix и cross-language process/schema boundaries.

**Владельцы:** scanner, language extractors, manifests, unknown taxonomy, fixture matrix.

**Pilot:** одна наблюдаемая cross-language boundary в mixed fixture и одном live repo
проходит `manifest/schema/process -> consumer` либо завершается точным typed stop.
Primary existing owner — scanner плюс соответствующие существующие language extractors.

**Propagation boundary:** одна ecosystem support cell за `S13.x`; новый parser не
появляется в том же подсрезе, что и второй unrelated ecosystem. Stop rule — отсутствие
task-changing live gap или external-verifier criterion.

**Реализация:**

- определить для каждого ecosystem support matrix: inventory, symbols, imports, packages, runtime,
  contracts, data, verification, dynamic unknowns;
- добавлять parser только для live gap, меняющего agent outcome;
- для форматов с высокой ценой regex-ошибки использовать лёгкий structured parser, не полный
  LSP по умолчанию;
- связывать languages через exact manifests, schemas, generated ownership, subprocess и protocol files;
- добавить `unsupported_language`, `unsupported_construct`, `external_runtime_boundary` в shared horizon;
- документировать versioned support matrix и не использовать слово «полная» для ecosystem,
  если не закрыт каждый указанный слой.

**Минимальный utility floor:** typed unknown доказывает честность, но не заменяет
полезное покрытие. Release manifest присваивает каждой ecosystem один tier:

| Tier | Обязательная наблюдаемая способность | Допустимое обещание |
| --- | --- | --- |
| A — flagship | inventory/package, symbols, static consumers, atlas, changed/proof и минимум одна ecosystem-specific runtime или contract/data цепь | Поведенчески проверенная структурная карта в перечисленных support cells |
| B — structural | inventory, manifests/packages, поддержанные symbols/imports/process boundaries, changed и точный coverage horizon | Структурная ориентация; без обещания полной runtime/contract lineage |
| C — inventory | file/git truth, bounded containers, unsupported classification | Только наблюдаемый inventory и координаты ручного погружения |

Flagship release требует не менее четырёх Tier A ecosystem families на шести
несвязанных live repos из S15. Каждая заявленная Tier A support cell имеет fixture,
live receipt и хотя бы один task criterion, outcome которого меняется при её потере.
Tier C не может называться ecosystem support. Рост typed unknown повышает честность,
но не закрывает отсутствующую Tier A/B способность.

**Доказательство:** fixture per support cell; six unrelated live repos across at least four ecosystems;
false-positive corpus.

**Исключено:** every language/framework in one release, compiler-equivalent semantics.

**Закрыто, когда:** выполнен Tier A floor, каждая ecosystem имеет release-declared tier,
а неподдержанный проект всё ещё получает полезный inventory/manifest/git map и честный
край видимости вместо пустого или ложно полного ответа.

read-only tool без привязки к одной модели или IDE.

**Сквозной сценарий:** agent получает stable JSON или compact text, snapshot identity, exact expands,
exit semantics и никакой скрытой мутации.

**Владельцы:** CLI, schemas/manifest, bootstrap, docs, exit codes, package/distribution metadata.

**Pilot:** один black-box agent harness получает exact JSON report, исполняет argv-form
Expand и отличает valid empty map от invalid anchor без readable parsing. Primary
existing owner — CLI/schema manifest.

**Propagation boundary:** второй независимый harness, OS/path matrix и optional adapter
идут отдельными receipts. Stop rule — adapter, которому нужна новая семантика, считается
новым продуктом и не входит в S14.

**Реализация:**

- определить stable exit code taxonomy: success, valid empty map, invalid anchor/config, unsupported request,
  stale/corrupt diagnostic, unsafe execution refused, internal error;
- каждый public JSON report имеет schema, report kind/version, build identity, scope, snapshot, horizon;
- опубликовать короткий agent protocol без task routing: exact anchor first, root only for orientation,
  expand by question, changed/proof after edits;
- унифицировать output to stdout, progress/diagnostics to stderr;
- проверить paths with spaces, Unicode, symlinks, subdirectory roots, Windows separators;
- добавить shell completions и machine-readable schema manifest;
- не добавлять hosted service, MCP или daemon как обязательную границу; они могут быть
  адаптерами над CLI после прохождения S15;
- после S15 допустим optional `codemap mcp` stdio-adapter в том же binary, если его tools однозначно
  проецируют existing CLI/schema surfaces, не добавляют семантики и проходят parity tests.

**Доказательство:** black-box CLI contract suite on macOS/Linux/Windows; schema compatibility tests;
two different agent harnesses.

**Исключено:** model-specific prompt router, hidden context injection, network dependency.

**Закрыто, когда:** интеграция не зависит от нестабильного readable parsing и не нарушает
zero-write contract.

### S15. Гейт поведенческого evidence

**Мир после среза:** каждое flagship-утверждение о полезности опирается на парное
измерение полноты и эффективности, а не на token compression или self-report агента.

**Сквозной сценарий:** одинаковые agents на одинаковом commit решают аналитические и
многофайловые implementation-задачи. Внешние criteria измеряют behavior, contract,
downstream и regression completeness. Токены и время — цена, а не победитель.

**Владельцы:** `scripts/benchmark-codemap-ab.py`, manifests, external verifiers, report docs.

**Pilot:** существующий `main_cluster` analysis pair воспроизводится из frozen manifest
с exact model/binary/repo provenance и теми же external criteria. Primary existing
owner — текущий A/B harness; новый scoring service не создаётся.

**Исходное evidence:** simple one-file task уже показал нулевой quality lift и большую цену;
`main_cluster` analysis уже дал положительный task-specific lift. Эти прогоны — baseline и две
обязательные regression tasks корпуса, а не отсутствующее «первое измерение».

**Два уровня прогона:** каждый поведенческий срез имеет 1–2 targeted paired tasks, доказывающие
его decisive scenario. Полная матрица ниже запускается как release/nightly flagship gate, а не как
обязательный PR-check.

**Реализация:**

- до accepted runs заморозить `CorpusManifest`, `TaskManifest`, rubric, pair order,
  prompts, model/reasoning settings, repo commits и правила invalidation;
- разделить corpus внутри каждого task class минимум поровну на `calibration` и
  `holdout`; holdout не используется для изменения extractors, prompts, budgets или weights;
- обе руки получают один task prompt и одинаковые tools/permissions/time limits;
  единственное плановое различие — доступ к codemap и опубликованному exact-entry protocol;
- counterbalance определяет, какая рука исполняется первой; состояние repo/cache между
  руками изолируется и приводится к manifest-defined baseline;
- повторы сначала агрегируются внутри task, затем tasks внутри repo, затем repos
  macro-усредняются; один большой repo не может доминировать количеством criteria;
- все exclusions применяются только по заранее перечисленным machine-checkable reasons;
  rejected и missing pairs остаются в report denominator;
- calibration results маркируются development evidence и не участвуют в flagship acceptance.

**Нормативная rubric:**

```txt
Criterion {
  id
  task_id
  category: required | behavior | contract | downstream | regression | provenance
  weight
  scoring: deterministic | ordinal
  external_verifier_or_blind_judge_protocol
  evidence_surface
}
```

Weights и criteria фиксируются до запуска holdout. Implementation criteria по возможности
имеют deterministic external verifier. Analysis criteria оценивают два независимых blind
judge, не видящих arm и resource usage; расхождения проходят blind adjudication.
Krippendorff alpha публикуется по каждой ordinal rubric; значение ниже `0.67` делает
соответствующий субъективный aggregate непригодным для acceptance до уточнения rubric и
нового frozen run.

**Матрица:**

- не менее 6 несвязанных repos и не менее 4 ecosystem families;
- 12 сложных analysis tasks;
- 12 multi-file implementation tasks со скрытыми consumers/contracts/regressions;
- 6 exact/local negative-control tasks;
- не менее 3 парных повторов на task и counterbalanced order;
- external deterministic verifiers для implementation;
- blind counterbalanced judging и manual audit sample для analysis;
- exact model, reasoning, Codex version, binary hash, repo SHA и invalid-pair reasons в receipt.

**Flagship acceptance:**

| Метрика | Граница |
| --- | --- |
| Primary endpoint | Holdout repo-macro weighted completeness delta; one-sided 95% paired bootstrap lower bound по tasks выше `0` |
| Required outcomes | Ни одного deterministic required regression против control |
| Complex-task wins | Положительный median task delta и не менее 60% holdout task wins; повторы не считаются отдельными tasks |
| Hidden downstream/contract/regression criteria | Не хуже control в каждой категории |
| Median complex-task time overhead | Не более 20% либо проходит pre-registered completeness exception ниже |
| Median complex-task input overhead | Не более 15% либо проходит pre-registered completeness exception ниже |
| Exact/local negative controls | Тот же outcome; median overhead не более 10% после exact-entry protocol |
| Repository writes in analysis mode | 0 |
| Invalid/ambiguous provenance | 0 принятых пар |

Превышение resource boundary не является автоматическим проигрышем, если полнота реально
выше. Для исключения по этой оговорке дополнительные выигранные criteria должны быть
pre-registered, а report показывает delta полноты рядом с delta ресурса по каждому task.
Completeness exception проходит только если primary endpoint принят, negative controls
остались в своём budget, и не менее 60% over-budget complex tasks имеют положительный
delta по заранее взвешенным criteria без required regression. Post-hoc объяснение не
меняет acceptance. Без pre-registered дополнительной полноты рост токенов/времени
считается неэффективностью.

**Доказательство:** immutable manifests и hashes; raw pair receipts; verifier outputs;
blind-judge assignments и agreement report; paired-bootstrap notebook/script; отдельные
calibration и holdout summaries; воспроизведение минимум одним независимым harness run.

**Исключено:** one-repo marketing claim, same-model score as sole truth, token compression as agent lift.

**Закрыто, когда:** frozen holdout проходит все строки Flagship acceptance,
calibration отделён от доказательства, raw receipts воспроизводимы, а exact/local
negative controls подтверждают отсутствие дорогого ритуала.

### S16. Дистрибуция и целостность release

**Мир после среза:** пользователь устанавливает одну проверяемую сборку `codemap` и получает
одинаковую семантику на поддержанных платформах.

**Сквозной сценарий:** Git tag создаёт checksummed macOS/Linux/Windows artifacts, package registry
release, changelog, schema compatibility receipt и smoke на чистой машине.

**Владельцы:** Cargo metadata, CI/release workflows, README, schema policy, packaging.

**Реализация:**

- получить clean release worktree и цельную commit history по vertical slices;
- добавить Windows CI к существующим Linux/macOS gates;
- добавить release workflow с signed/checksummed artifacts и binary identity;
- опубликовать crates.io или equivalent registry; добавить Homebrew после стабильного artifact URL;
- не паковать fixtures/tests/internal plans в runtime package, если они не нужны для сборки;
- добавить `CHANGELOG.md`, `SECURITY.md`, support matrix, cache/privacy и compatibility policy;
- проверять install/upgrade/downgrade и cache format migration/invalidation;
- не публиковать release как `flagship`/stable flagship, если S15 не прошёл
  flagship gate. Maintenance/patch release до S15 допустим, если он не заявляет
  flagship-замыкание, проходит текущий release contract и явно сохраняет
  незакрытые flagship-границы в limitations/release notes.

**Доказательство:** `cargo package`, clean-container install, OS matrix smoke, checksum verification,
schema backward compatibility, upgrade cache smoke.

**Исключено:** auto-update, telemetry, hosted account, network dependency in CLI.

**Закрыто, когда:** версия из tag, package registry, downloaded binary, `doctor` и benchmark receipt являются
одной и той же проверяемой сборкой.

### S17. Flagship-замыкание

**Мир после среза:** `codemap` — чисто поставляемая, быстрая, схематичная и доказанно
полезная карта внимания для агента.

**Сквозной сценарий — финальный:** на чистой машине новый агент:

1. устанавливает release binary;
2. открывает незнакомый mixed monorepo;
3. получает current-level atlas;
4. переходит к exact anchor;
5. видит consumers, runtime, contract/data, deployment и verification paths с evidence;
6. видит hidden/unsupported/dynamic horizon;
7. делает многофайловое изменение;
8. получает session-local structural delta;
9. видит verification topology без вердикта;
10. не обнаруживает ни одной записи `codemap` в target repo;
11. воспроизводит тот же результат из JSON/schema-backed API;
12. завершает более полный external-verifier task, чем paired control, в границах S15.

**Владельцы:** операционный статус этого документа и existing release/schema/benchmark
owners. S17 не создаёт нового orchestrator.

**Реализация:** не добавлять новую семантику; собрать immutable receipts S00–S16,
воспроизвести финальный сценарий released binary и сопоставить каждое публичное
утверждение с receipt ID.

**Доказательство — final gate:**

```txt
clean git worktree
one released binary identity
cargo fmt --check
cargo test
cargo clippy --all-targets -- -D warnings
version/schema compatibility guard
doctor and cache corruption/write-failure probes
strict cognitive and performance gates
zero-footprint probes
six-repo live dogfood
behavioral A/B corpus acceptance
fresh-install OS matrix
independent contract review
```

**Исключено:** новая линза, новый parser, hosted surface, изменение benchmark rubric
или ослабление budget после просмотра final results. Любая такая потребность возвращает
работу в соответствующий предыдущий срез.

**Закрыто, когда:** каждое утверждение README и release notes прямо опирается на один
из этих receipts, выполнены S13 utility floor и S15 holdout acceptance, а все
известные map-semantic границы либо исправлены, либо видимы в самой карте как
typed horizon. Операционные, distribution-, performance- и governance-границы
закрываются собственными receipts или остаются явными в limitations/release notes;
они не маскируюются как map `Unknown`.

## 10. Порядок реализации и публикации

1. В один момент активен один срез.
2. Следующий срез не начинается, пока не закрыт decisive scenario текущего.
3. Каждый срез проходит через existing owner module; новый owner создаётся только при
   отсутствии подходящего.
4. Shared model/schema/cache/scanner/git-state срез требует full gate и независимый review.
5. Renderer-only работа не открывается без конкретного confusing/false live output.
6. После каждого закрытого среза:
   - фиксируется `closed / excluded / evidence`;
   - делается conventional commit;
   - push выполняется только из цельного чистого состояния;
   - artifact receipt хранится в `target/` или вне repo, если он не является необходимым
     regression fixture.
7. Если live/A/B result показывает более сильную форму, контракт уточняется вокруг
   неё, а не вокруг прежней слабой реализации.

## 11. Признаки drift

Работа останавливается и возвращается к текущему decisive scenario, если появляется
один из признаков:

- новая линза без нового agent outcome;
- новый renderer для факта, уже представленного в shared grammar;
- новый parser без live false-negative/false-positive;
- оценка или recommendation, замаскированная под structural fact;
- мягкая связь, повышенная до hard/high для красивого output;
- root output, растущий вместе с repo;
- hidden output без count и exact expand;
- test, который проверяет слово, но не защищает поведение;
- полировка при незакрытом false map edge;
- зелёный fixture без live/A/B прохода там, где срез обещает agent outcome;
- новый командный ritual вместо более сильного exact anchor.

## 12. Конечное обещание

Завершённый `codemap` не говорит агенту, что думать. Он даёт ему лучшую
наблюдаемую форму того, о чём нужно думать самому:

```txt
вот текущий уровень
вот точный anchor
вот наблюдаемые стороны
вот отношения и их происхождение
вот границы и преобразования
вот найденные поверхности проверки
вот чего карта не видит
вот сколько скрыто
вот точные лупы для следующей глубины
```

Это и есть flagship-карта: не суд, не роутер задач и не энциклопедия, а правдивая
прогрессивная лупа, которая полнее направляет внимание агента и оставляет
мышление ему.
